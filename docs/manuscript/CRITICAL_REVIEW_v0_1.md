# Critical review — Preprint v0.1

**Reviewer:** internal pre-submission adversarial pass
**Date:** 20 September 2026
**Manuscript:** `docs/manuscript/preprint_v0_1.md` (commit `3827c65`)
**Verdict:** MAJOR REVISION required before external release. Three substantive Methods errors (the manuscript describes an intended-but-not-implemented scoring rule), plus two dead reference URLs, plus several editorial issues. None of the substantive results (H1/H2/H3 conclusions) are wrong — but the Methods section as written does not reproducibly describe the AlphaGenome scoring that actually generated them, and that is the highest-impact fix.

## Category A — Substantive Methods errors (must fix before release)

### A1. The AlphaGenome scoring rule described in Methods is not the rule implemented in the Colab notebook

**Preprint claim (Methods, AlphaGenome subsection):**

> "The score used for hypothesis testing was the absolute change in predicted junction usage at the canonical junction closest to the variant, computed as |usage(REF) − usage(ALT)| in the default lung/bronchial-epithelial cell context."

**What the code actually does** (`scripts/colab_alphagenome_scoring.ipynb`, cell 4):

```python
splicing_scorers = [
    vs.RECOMMENDED_VARIANT_SCORERS['SPLICE_SITES'],
    vs.RECOMMENDED_VARIANT_SCORERS['SPLICE_SITE_USAGE'],
    vs.RECOMMENDED_VARIANT_SCORERS['SPLICE_JUNCTIONS'],
]
# per variant, three scorers each aggregated as max(abs(raw_score)) across
# all genes and tracks in a 1 Mb interval, then combined:
ss  = max_abs(df, 'SPLICE_SITES')
ssu = max_abs(df, 'SPLICE_SITE_USAGE')
sj  = max_abs(df, 'SPLICE_JUNCTIONS')
score = ss + ssu + sj / 5.0
```

Three specific discrepancies with what Methods says:

- **The score is a composite of three AlphaGenome variant-scorers**, not a single per-junction usage delta. The three scorers (`SPLICE_SITES`, `SPLICE_SITE_USAGE`, `SPLICE_JUNCTIONS`) each produce their own signal, and the final per-variant score is `SPLICE_SITES_max + SPLICE_SITE_USAGE_max + SPLICE_JUNCTIONS_max / 5`. The `/5` weighting on the junctions channel is not motivated in any protocol document and is not pre-registered.
- **No cell-type filter is applied.** `max_abs` takes the maximum absolute raw score across the entire tidy-scores DataFrame for each scorer — every gene, every track. There is no restriction to lung, bronchial epithelium, or any UBERON ontology term. The Methods claim of "default lung/bronchial-epithelial cell context" is inherited from the pre-registration protocol (`docs/protocol/methodology_v1.md` §4.1) and from the indices document (`docs/protocol/indices_and_derived_variables.pdf` §1), but it is not what the Colab notebook implements.
- **No canonical-junction selection is applied.** The Methods sentence "at the canonical junction closest to the variant" describes an operation the notebook does not perform. The notebook aggregates over all junctions in the 1 Mb interval that AlphaGenome returns.

**Severity:** high. This is the single most reproducibility-critical paragraph in the paper. As written, the Methods section describes an idealised scoring rule from the pre-registration protocol; the paper reports results generated by a different rule. A reviewer who tries to reproduce the scoring from Methods alone will produce different numbers.

**Recommended fix:** rewrite the AlphaGenome scoring paragraph to describe the composite `ss + ssu + sj/5` rule that was actually used, state which three variant scorers were called, note that aggregation is `max(abs(raw_score))` across genes and tracks (no cell-type filter), and acknowledge that this composite deviates from the pre-registered `|usage(REF)−usage(ALT)|` at the canonical junction. Add a paragraph to the Discussion Limitations subsection making the deviation explicit and flagging it as a pre-registration deviation. Update `docs/protocol/AMENDMENTS.md` with an amendment recording the deviation.

### A2. AlphaGenome was queried via Colab notebook, not "the release version of the AlphaGenome API"

**Preprint claim (Methods):**

> "AlphaGenome was queried via the release version of the AlphaGenome API on 14 September 2026."

**What actually happened:** access was through the `alphagenome` Python SDK inside a Google Colab notebook (`scripts/colab_alphagenome_scoring.ipynb`), because the sandbox proxy could not inject credentials into the gRPC calls the SDK uses. The 14 September 2026 date is the courtesy-notification date to DeepMind, not the scoring date. The actual TSV was received on or after 15 September 2026 (once the reply came back and the notebook was run). The file timestamp of `results/predictions/alphagenome.tsv` is 20 September 2026 in this workspace, but that reflects the local copy; the OSF/GitHub archive preserves the original.

**Severity:** medium. Reproducibility improvement, not a scientific error. But a reviewer who wants to re-score the variants needs to know they need a Colab notebook with an AlphaGenome API key and the `alphagenome` SDK, not a bare-metal API call.

**Recommended fix:** replace "via the release version of the AlphaGenome API" with "via the `alphagenome` Python SDK executed in a Google Colab notebook (`scripts/colab_alphagenome_scoring.ipynb`)"; give the actual scoring date; note that the notebook is not in the repository because `.ipynb` files are gitignored per repository policy, and provide either a `.py` conversion in the repo or a note that the notebook is available on request.

### A3. Interval sizing is not stated in Methods

The Colab notebook centres each variant in a **1 Mb interval** (`SEQ_LEN = dna_client.SEQUENCE_LENGTH_1MB`) before calling `model.score_variant`. Methods says nothing about this. Reviewers familiar with AlphaGenome will assume it, but the paper should state it explicitly because AlphaGenome supports shorter intervals and the choice materially affects the tracks that contribute to the score.

**Recommended fix:** add one sentence: "Each variant was centred in a 1 Mb reference interval (`dna_client.SEQUENCE_LENGTH_1MB`) for scoring."

## Category C — Statistical and inferential concerns a reviewer will raise

### C1. Perfect discrimination at n=52 with 9 negatives — reviewer will ask about bootstrap CI width

The Results state a bootstrap 95% CI of `[1.000, 1.000]` for AlphaGenome's Stratum 2 AUC. With n=9 negatives, the DeLong SE for a perfect AUC is degenerate (variance term is zero by construction), and stratified bootstrap on 9 negatives can trivially return `[1.000, 1.000]` if the resamples never disturb the perfect separation. This is technically correct but hides that the *effective* uncertainty at n=9 negatives is much wider than the CI suggests. A reviewer will ask for a Bayesian interval (e.g. Jeffreys interval on a proportion-equivalent) or a Wilson-style CI for AUC=1, both of which give much wider intervals.

**Recommended fix:** either compute and report a wider small-sample CI (e.g. an exact CI for AUC=1 at n_pos=43, n_neg=9 using the Newcombe-Hanley or Cortes-Mohri formulation) as a supplementary robustness check, or explicitly acknowledge in Limitations that the `[1.000, 1.000]` CI is a small-sample bootstrap artefact and that the true small-sample uncertainty on AUC=1 with n_neg=9 is much larger than the interval suggests.

### C2. Reviewer will ask why the H3 direction is descriptive not inferential

The paper states H3 is "descriptive" and reports Spearman ρ with bootstrap CI but no p-value or formal decision. This is defensible (pre-registered) but a reviewer will ask: (a) why H3 was descriptive when a one-sided permutation test at n=8 is feasible and pre-registerable; (b) whether the descriptive-only framing was decided before or after seeing that ρ=−0.66 with a bootstrap CI that crosses zero. The pre-registration date (13 Sep) and scoring date (post 15 Sep) support the "before" answer, but the paper doesn't say so explicitly.

**Recommended fix:** add one sentence to Methods H3 subsection: "The descriptive framing was pre-registered on 13 September 2026 before any predictor was scored (see OSF registration), on the basis that n=8 was too small to support a formal inferential test with useful power."

### C3. Sample-size justification for Stratum 2 is missing from Methods

The paper reports n=52 on Stratum 2 but does not state whether that was a pre-specified target, a post-hoc availability count, or the result of a power calculation. From `docs/protocol/methodology_v1.md`, n=52 was the harvestable count from Joynt et al. — a data-availability constraint, not a power target. Methods should say so.

**Recommended fix:** add one sentence: "The Stratum 2 sample size (n = 52) was fixed by the number of variants systematically characterised by Joynt et al. (2020); no power calculation was performed because the harvest was availability-limited, not effect-size-limited."

### C4. Reviewer will ask about training-data contamination

AlphaGenome, SpliceAI, and Pangolin were all trained on human genomic data that included chr7 / *CFTR*. If any of the 60 benchmark variants (particularly the Joynt et al. 2020 variants) appeared in the training splits of any of the three predictors, that would be train-test leakage. This is a real concern that Methods does not address.

**Recommended fix:** add a Limitations paragraph on training-data contamination. Note the training-data sources of each predictor (SpliceAI: GENCODE canonical protein-coding transcripts, no ClinVar; Pangolin: RNA-seq splice-site usage from four tissues in four species; AlphaGenome: ENCODE + GTEx + 4DN + FANTOM5) and state whether any of the 60 benchmark variants were in the training splits of any predictor. If unknown, say so honestly ("training-set leakage cannot be ruled out because the training-variant lists of AlphaGenome, SpliceAI, and Pangolin are not exhaustively published"). This is not fatal but must be acknowledged.

### C5. Reviewer will ask about multiplicity across H1/H2/H3

Three hypotheses tested, no multiplicity correction. This is defensible because H1 is primary and H2/H3 are secondary and pre-registered, but the paper should state the multiplicity policy explicitly.

**Recommended fix:** add one sentence to Methods: "Because H1 is primary and H2/H3 are pre-registered secondary hypotheses with distinct decision rules (non-inferiority for H2, descriptive for H3), no multiplicity correction was applied; the reported p-values are per-hypothesis nominal values."

## Category D — Interpretive and framing issues

### D1. Non-inferiority CI vs SpliceAI is reported twice with the same lower bound (−0.012), which is misleading

The Abstract and Results both report the non-inferiority CI lower bound as "−0.012" for both SpliceAI and Pangolin comparisons. Reading the raw JSON, the two lower bounds are `−0.011505` (vs SpliceAI) and a different value (vs Pangolin) — the Abstract rounds both to −0.012. A reviewer who checks the numbers will find that "both CIs' lower bounds = −0.012" over-collapses the two results. It's not wrong but it reads as though the two comparisons produced identical CIs.

**Recommended fix:** report the two lower bounds to three decimal places separately, or add a "both well above the −0.05 margin (see Table X)" phrasing that doesn't imply equality.

### D2. The prior-recalibration paragraph in Discussion is well-written but should signal its own limits

The "Prior on a perfect result" subsection is one of the best paragraphs in the paper but it is one-sided: it argues why the naive symmetric prior undersells AlphaGenome. It doesn't note the *other* prior asymmetry: AlphaGenome is newer and its training data is much larger, so a Bayesian who conditioned on scale-of-training would also expect it to do slightly better than the two older comparators on the same task. That is not the strong version of the argument the paragraph is making (which is about architecture/objective), but a reviewer will notice it's absent.

**Recommended fix:** add one sentence: "Conversely, a prior conditioning on training-data scale alone would also favour AlphaGenome; the architecture/objective argument above is intended as a stronger claim than the training-scale one, not as a substitute for it."

### D3. "Perfect rank separation" wording is repeated four times

The phrase "perfect rank separation" appears in the Abstract, Introduction, Results, and Discussion. It's factually correct each time but it's the paper's headline result and a reviewer will notice the repetition. Two of the four uses should be re-phrased.

**Recommended fix:** vary the phrasing in Introduction and Discussion: "AlphaGenome was the only predictor to correctly rank all 43 splice-affecting variants above all 9 no-effect variants" (once), "AlphaGenome achieved ROC-AUC = 1.000 on Stratum 2" (once), etc.

## Category E — Editorial and formatting

### E1. Correspondence line is uninformative

> "Correspondence: via the OSF project record ([osf.io/5hvgf](https://osf.io/5hvgf/))."

Journals require a name and an email address for corresponding author. Even for a preprint, "via the OSF project record" is unusual and will confuse readers who want to contact the author.

**Recommended fix:** provide a real email (institutional NHS or academic) for corresponding-author contact.

### E2. Preprint header lacks ORCID, department, and funding statement

Standard preprint template expects ORCID, department affiliation (not just "Barts Health NHS Trust" but the specific department/rotation), and either a funding statement or a "no funding received" line.

**Recommended fix:** add ORCID (if you have one), department, and funding-statement line before submission.

### E3. Figures block position is fine but figure paths are relative

The preprint embeds figures with relative paths `../../figures/figure1_roc_stratum2.png`. This resolves correctly from `docs/manuscript/preprint_v0_1.md` but will break in any rendering that flattens the directory structure (e.g. copying just the preprint file into a submission portal).

**Recommended fix:** for the submission version, either (a) copy the two figures into `docs/manuscript/` and use bare filenames, or (b) render to PDF (in which case the images are embedded and paths stop mattering).

### E4. "Table 1" is missing

A benchmark paper with 60 variants should have a Table 1 listing the variants, their strata, their ground-truth values, and the three predictor scores per variant. Currently this data is in `data/variant_list_frozen.tsv` and `results/predictions/*.tsv`. A reader who wants to see per-variant results cannot without cloning the repo.

**Recommended fix:** generate a Supplementary Table 1 (either markdown table in the preprint, or a linked TSV/CSV in the release) with variant_id, HGVS c., stratum, ground truth, and per-predictor score. This is standard for benchmarking papers.

### E5. Small typo/consistency issues

- Discussion §"Comparison with the AlphaGenome preprint" says "AlphaGenome's original evaluation on ClinVar splicing variants reported a stronger separation from SpliceAI/Pangolin than this study shows on CFTR" — but the AlphaGenome preprint's ClinVar benchmark is a broadly-similar benchmark, not one showing "stronger separation." Verify the claim against the AlphaGenome preprint or reword to "similar or better separation" until verified.
- Methods says "the researcher's non-commercial affiliation (Barts Health NHS Trust)" — in a single-author preprint written by the researcher, "the researcher" reads oddly. Prefer first-person or third-person consistently (Robert English, or "the author").
- Abstract uses en-dashes for ranges (e.g. "10–15%") which is correct; verify that hyphens vs en-dashes are consistent throughout the preprint.
- Results Summary paragraph says "approximately twice the magnitude of the comparators" (0.66 vs 0.32/0.29) — this is factually 2.05× and 2.28×, so "approximately twice" is accurate but "roughly double" is more common in scientific writing.

## Category F — Legal / compliance

### F1. `LEGALLY_BINDING_ALPHAGENOME_OUTPUT_TERMS.txt` — verify content is current

Methods (A1.2) says this file quotes the notice text prescribed by Model Terms Section 3(c) and Output Terms Section 3. Given that the actual URLs in Ref 17/18 are 404 (see B1), the notice text you quoted was drawn from an older version of the terms. Verify against the current `alphagenomedocs.com/licenses/` version.

### F2. The A1.1 "summary-statistics-only rule" language conflicts with the actual composite score

The A1.1 control says "No logistic regression, calibration, isotonic regression, meta-classifier, ensemble, or other parameter fitting is applied to AlphaGenome output." The `ss + ssu + sj/5` composite (see A1) is arguably a linear combination of three AlphaGenome outputs with hand-chosen weights (1, 1, 1/5). It is not a *fitted* model, so it does not violate A1.1's letter. But a strict reader could argue that any weighted combination is a form of ensembling, and the /5 weight is arbitrary and undocumented. The safer path is either (a) drop the composite and use one of the three scorers directly, or (b) explicitly state in Methods that the composite uses fixed, un-fitted weights and cite the source (AlphaGenome documentation, if it recommends this composite) for the weights.

**Recommended fix:** review the AlphaGenome documentation for whether the `ss + ssu + sj/5` composite is a documented recommended score or an ad-hoc choice. If it is documented, cite the source. If not, either drop the composite (use one scorer, pre-register the choice) or acknowledge it as an ad-hoc combination and rerun the analysis with the three scorers individually as a sensitivity check.
